## Summary

Ticket: SWM-179. PR ix-relay#44, branch codex/swm-179-dashboard-navigation-implementation at frozen head 0f602f65ca06a90390b01aecff326e4d2b0887db (base main c2f3dff). Code-review method with the Rust lane (rust-review and rust-style) and a docs check of the two changed documents folded into this one artifact. The change implements FR-065: one View selector and dropdown, one F1 help popup, a one-row footer, bounded evidence rows, shared identity row, department population labels, a Status purpose line and Health and Retro empty states, in relay-tui only.

The production design is sound. Popups are one `Option<Popup>` in `App`; `handle_key` hands every key to an open popup first and `handle_popup_key` acts only on the keys the popup owns, so `q`, `r`, `d`, Enter and the view keys cannot leak; both popups draw only inside the work area rect; dropdown arithmetic and help scroll clamp at draw time; selecting a view goes through the same `select_view` as the compatibility key; terminal setup, signal handling and the event loop are unchanged and no mouse capture exists. 12 findings: 5 medium, 7 low, no high. The mediums are a triplicated helper, a Retro/Health instruction that cannot be followed in lead-only startup, a Status row that now claims a collection is awaited when none is configured, and two test oracles that cannot fail for the interaction they are tagged to.

## Finding details

### FND-001 (medium) The `muted` helper now exists three times

Rule: code-review "Duplication inside one repo": a new helper that duplicates an existing function's behavior is a fail; the same fragment defined twice is a fail. Search done: I grepped `fn muted` under crates/relay-tui/src. It finds monitor_ui.rs:719 (existing, private, generic lifetime) and the two new copies monitor_department.rs:524 and monitor_nav.rs:131. All three bodies are `Span::styled(text, Style::default().fg(MUTED))`. monitor_department.rs already imports `MUTED` and the other shared helpers from monitor_ui (`evidence_items`, `identity_line`, `selector_line`, `wrapped_rows`), which the PR made `pub(crate)` for that purpose, so the same step would have exported `muted`. Risk: a change to the muted style must be made in three places and one copy will be missed. Severity: this is in-repo duplication of a three-line helper, not vendoring, so the vendoring `high` rule does not apply; I grade it by consequence, medium. Judgement noted for the parent. Fix: make monitor_ui::muted `pub(crate)` and import it in both modules; delete the two copies.

### FND-002 (medium) The lead-only Not configured instruction cannot be followed

FR-065 Empty Health and Retro asks the live message to name `--retro-config <file>` whose population matches the selection in the label. For an explicit `--team` that is right. For a lead-only startup the label is `team SWM derived from lead workspace · all projects`, and `empty_message` (monitor_department.rs:645-655) says to start with `--retro-config <file>` whose population matches that. The startup check in `load_config` (monitor_department_source.rs:49-58) compares the configuration's department teams and projects with `args.team` and `args.project` only. In a lead-only run both are empty, because `department_team()` (monitor.rs:218-228) derives the team from the binding at render time and stores nothing, so a configuration for team SWM is refused at startup with `--retro-config department team/project population must exactly match --team and --project selectors`. The message never says to also pass `--team`. The AC-9 test (monitor_department.rs:1320) covers an explicit team only, so this branch has no fixture. The wording is the one FR-065 asked for, so the cause is shared with the spec; the defect is that the user-facing guidance is not actionable. I could not run the loader to confirm that no empty-scope configuration is accepted, so confidence is medium. Fix (text only, no behavior): in the derived case name `--team <KEY>` next to `--retro-config` and say the configuration's population must equal the command's selectors; add a fixture for the derived label.

### FND-003 (medium) Status says a collection is awaited when none is configured

Before this change `run` set `app.department.failure("Department health/retro unavailable: supply --retro-config ...")` whenever neither `--report` nor `--retro-config` was given, and every department view, Status included, showed it as a failed source with that guidance. The PR removed that line (monitor_main.rs:149-150) because Not configured is not a failure, which is right for Health and Retro. Status has no Not configured state: `empty_message` returns `None` for it. With no department worker, `status_rows` (monitor_department.rs:428-435) adds `Capacity / lane activity: unavailable / No department report / Awaiting shared collection; capacity and liveness are not inferred.` and no evidence row remains. Risk: `team-leader-dashboard --team SWM` opens on Status (monitor_main.rs:341-345), and the row now tells the user to wait for a collection that is never scheduled, with nothing on the screen explaining why; this is the friction the ticket opened with. FR-065's list of permitted differences covers the Health and Retro state display only, so a changed Status explanation was not in the list either. Fix: for `DepartmentInput::NotConfigured` make that row say that no retro configuration was supplied and name `--retro-config <file>`, still without a failure row; add a Status fixture for the no-config state.

### FND-004 (medium) The live AC-10 oracle cannot fail for the interaction it names

Test `live_popups_run_the_real_loop_with_held_reads_and_no_new_calls_or_writes` (monitor_main.rs:702-803) starts the real `TrackerWorker` and `DepartmentWorker` with reads that block on `tracker_held.recv()` and `department_held.recv()` (lines 725-730, 739-744) and releases them only after every assertion (lines 800-801). The script presses `r` while each popup is open (popup_script, lines 590 and 595). If `handle_key` leaked `r` to the refresh path, the loop would call `refresh_now()`, which is `commands.try_send(...)` onto a worker that is still inside the held read (monitor_ops.rs:157-159); no second read can start before the assertions, the `calls` counters stay at 1 and 1 or 0, and the loop clears `app.refresh_now` itself (monitor_main.rs:266), so `assert!(!app.refresh_now ...)` at line 777 cannot fail either. The stated oracle, no new tracker or department read, can therefore not detect the only mechanism by which a popup could start a collection. It is partly covered at unit level by the AC-4 test, which asserts `!app.refresh_now` after each foreign key, so the leak is not undetected overall; the AC-10 live claim itself is satisfied vacuously. fix1-ready.md section 2 presents this fixture as proving the point. Fix: release the held reads before the last idle ticks and quit, give the loop a few ticks, and then assert the counters; a leaked refresh queued during the popup then starts a second read and the count rises to 2. Keep one case with the read still held to prove the loop does not block on it.

### FND-005 (medium) Fixed texts are asserted against the production constants

FR-065 states the exact department relation text and the exact Status purpose line, and AC-7 and AC-8 require tests that assert them. The production constants are `DEPARTMENT_RELATION` (monitor_department.rs:29-30) and `STATUS_PURPOSE` (32-33). The tests assert `text.contains(DEPARTMENT_RELATION)` (line 1281), `drawn.contains(DEPARTMENT_RELATION)` (1288) and `text.contains(STATUS_PURPOSE)` (1308), the value the code under test supplies. A grep for the literal strings under crates finds them only in the two constant definitions. Rust-style testing: an assertion on a value the test itself supplied does not measure production behavior. A typo or rewording of either constant keeps AC-7 and AC-8 green. The Agents label has the opposite, correct shape: its test (monitor_ui.rs:1858) asserts the literal text. Fix: assert the FR-065 literal strings in the tests (the two assertions at 1281 and 1308 can keep a second check against the constant if wanted).

### FND-006 (low) The saved-report AC-10 oracle is not what its message says

In `saved_report_popups_run_the_real_loop_without_any_adapter_call_or_write` the counter `reads` wraps only the closure passed to `prepare_app` (monitor_main.rs:654-659). The loop's refresh path calls `monitor_department_source::read_report(path)` directly (monitor_main.rs:261), which the counter cannot see, so `assert_eq!(reads.get(), 1, "no saved re-read: refresh never fired")` at line 685 is always true. The fixture does still fail for a leaked `r`, because the file holds the bytes `saved report bytes` (line 646), the real reader errors and `app.department.error` becomes set, which line 688 rejects. Separately the panicking Herdr and credential closures (lines 660 and 663-665) run during setup, before the loop, and the loop is given no adapter, so they say nothing about popup interaction. Fix: delete the misleading counter assertion or count the loop's reader through a seam, keep the error assertion as the oracle, and say in a comment that the adapters are unreachable from the loop by construction.

### FND-007 (low) The help reachability assertions are vacuous for short keys

`every_help_line_is_reachable_at_80x24_and_f1_question_and_escape_close_it` (monitor_nav.rs:554-592) concatenates 40 frames and asserts `seen.contains(entry.keys)` and `seen.contains(entry.owner)` for each help entry (lines 575-578). For the single-letter entries `v`, `r`, `s`, `e` and `c` the containment is satisfied by text elsewhere on the frame (for example `v` and `s` in the selector line `View: Tickets ▾  v opens the list`, which every frame carries), so those five entries prove nothing about the popup. The second line of every entry (`Views: ...`) and the header lines are never asserted. A regression that stops the scroll one line early, so the last `Views: all` line is unreachable, passes. FR-065-AC-3 says every line is reachable. The resize assertion `after <= scroll` (line 590) also holds when nothing is clamped. Fix: assert that the final `help_lines(view)` line appears in the concatenated frames, and that the scroll after resize equals the clamped value for the new height.

### FND-008 (low) Evidence severity is an untyped number

`Evidence.severity` is a `u8` (monitor_ui.rs:324). `evidence_items` assigns 0, 1, 2 and 3 at ten `item(...)` call sites (lines 360 to 447), `sort_by_key` orders on it (453), and `evidence_lines` reads the numbers back with `match evidence.severity { 0 => failure, 1 | 2 => WARNING, _ => MUTED }` (493-497). The meaning of each number exists in two places, and any value above 3 silently becomes muted. Rust-style implementation: use a closed enum and an exhaustive match, never a catch-all that turns an unknown value into a valid one; keep a fact in one place. Fix: a small private enum (failure, rate-limit, stale, fact) with `Ord`, matched exhaustively for colour.

### FND-009 (low) Copied test helpers

`flat` in monitor_department.rs tests (1229-1231) is the same body as `flat` in monitor_scope_tests.rs:812-814. `draw` in monitor_nav.rs tests (349-363) repeats `screen` in monitor_ui.rs tests (1528-1542), and `last_frame` in monitor_main.rs tests (627-638) repeats the same cell loop a third time. Code-review duplication inside one repo: copy-pasted test setup that an existing helper provides. Fix: reuse `monitor_ui::tests::screen` and one shared `flat`; the monitor_main helper needs a `Terminal` argument, which the shared helper can take.

### FND-010 (low) New tests add matrix warnings

The quire matrix stderr (fix1-matrix-stderr.log) reports 21 `trace-id-outside-marker` warnings on FR-065 symbols, for example `FR-065-AC-1 is written in a comment or docstring on tests::dropdown_lists_every_view_and_selects_like_the_compatibility_key at monitor_nav.rs:365; a comment never binds`. Of the 21, 18 are the new tests (each carries both `/// Trace: FR-065-AC-n` and `#[trace("FR-065-AC-n")]`; the docstring line is what the engine flags) and 3 are comments that cite `FR-065` on `Popup` (monitor.rs:114), the monitor_nav.rs module header (line 3) and `HelpEntry` (line 29). The saved stderr already holds 25 warnings of this kind on FR-048, FR-059 and FR-060 tests in the same files, so the pattern predates the PR, but code-review Integrity says to fix warnings even when they look unimportant and not to add new ones. The attribute binds; the docstring line adds nothing. Fix: drop the `/// Trace:` lines from the 18 new tests, and for the three comments either remove the id or use `#[implements("FR-065")]` as the engine's message suggests.

### FND-011 (low) docs/department-monitor.md omits three empty states

Lines 33-36 say that without a configuration or saved report Health and Retro show a Not configured message and that they wait before the first read. The page does not say what a saved report that lacks the Health or Retro fields shows (`Not configured: this saved report does not supply the Health fields. Open a report that contains them with --report <file>.`), what a failed first read shows (`Health unavailable: <classified reason>`, with a Department failed row) or that a retained model is shown with its last-snapshot label. The reader of the `--report` section meets only `Plan fields absent from a saved report remain unavailable.` The other statements in the two changed documents match the code (keys, four evidence rows, footer, the three department selection forms, popup isolation, refresh continuing). docs-style was unavailable, see Review Context. Fix: add one sentence per state under the retro configuration paragraph and one in the saved report section.

### FND-012 (low) The `run` wiring of DepartmentInput is untested

`run` sets `app.department_input = department_input(&args, department_config.is_some())` (monitor_main.rs:149-150). The helper's mapping is exercised, but the call in `run`, which decides Configured against NotConfigured for a real start, is run by no test: the live AC-10 fixture sets the field by hand with `app.department_input = department_input(&live, configured);` (line 716). Removing the line in `run` would show Not configured to a user who supplied `--retro-config`, and every test would pass. Fix: factor the app construction used by `run` (prepare plus the input mapping) into one function that both `run` and the fixtures call.
