## Finding details

### FND-001 (medium) The typed outcome is captured only after a successful read

`read_tracker_with_factory` (monitor_ops.rs:371-386) calls `service.force_refresh_workspace()?` or `service.workspace_snapshot()?` and reads `service.refresh_outcome()` only in the `Ok` tail. On any error it returns at the `?` and drops the service, with its outcome. In the accepted SDK the outcome is set before the error leaves: `refresh` runs `self.outcome = RefreshOutcome::from_error(&error);` and then, when `cache.last_complete()` has no snapshot, `return Err(error.legacy_rate_limit());` (lib.rs:1123-1125 in both the frozen reference and the actual fcb0b35 checkout). `from_error` keeps the whole `QuotaDecision` for `QuotaAdmissionRefused` and maps `RefreshLockTimeout` to `RefreshLockRefused`. `legacy_rate_limit` (lib.rs:481-503) then rewrites a `QuotaAdmissionRefused` whose primary state is `ServerBackoff` into `LinearRateLimited { retry_after }`. `ServerBackoff` has the highest precedence of any state (quota_decision.rs:27-36), so any decision with an actual backoff, including one that also carries other blockers, is flattened to a bare duration exactly when the cache holds no snapshot. Consequences on the cold path: (1) the dashboard shows only `Linear rate limited`; the attempt, every other blocker, the pending legacy reservations and the earliest reevaluation that the SDK captured are gone, and the `retry_after` the error carries is not shown either; (2) a refused refresh lock with no snapshot reaches `Cause::of_error` as `RefreshLockTimeout`, which maps to `None`, so it is worded `Tracker failed` with the generic source-availability remedy, while the same refusal with a snapshot is the typed `Linear refresh lock busy`; the two paths disagree on one typed outcome. The test `without_a_snapshot_the_error_carries_the_typed_decision` (monitor_ops.rs:932-978) asserts `Some("Linear rate limited")` as the whole detail for a backoff and its docstring says the legacy error `stays the only rate limit`, so it pins the loss as intended. The coder's report records the limit (coder-ready.md, Limits) and ties it to the unbounded `refresh()` path; that explains the cause and does not meet the contract that all typed blockers and the actual attempt and earliest reevaluation are shown, nor the FR-048 sentence that a held refresh reports every blocker and the earliest reevaluation the service gave (see SR-1853 FND-003 for the gap that sentence leaves for a missing snapshot). Confidence high: traced end to end in the frozen reference and the actual checkout; I did not run it. Fix: capture the typed outcome on the failure path as well as the success path (for example, a failed read value that carries the error and the outcome read from the service after the failed call; a factory or credential error has no service and stays outcome-less), classify a failed read from the typed `QuotaRefused` decision first and the legacy typed errors second, show the backoff with its decision's blockers and earliest reevaluation, map `RefreshLockRefused` to the lock notice on both paths, and replace the pinned `Some("Linear rate limited")` with an assertion that a cold backoff that also carries a second blocker shows that blocker. No error text is parsed, and no compatibility shim is needed.

### FND-002 (medium) All blockers reach the screen only as the tail of one truncated row

The detail with the attempt, the legacy reservation count, the earliest reevaluation and every blocker is stored in `tracker.error` (`Notice::detail`, joined with `·`, summary first, blockers last). `evidence_items` attaches it as the detail of one evidence row (monitor_ui.rs:406-424; in the lead views `text()` returns the full `error`, monitor_ui.rs:366-375), and `evidence_lines` renders `label: detail` on one terminal line and truncates the detail to the remaining width with `…` (monitor_ui.rs:547-558). At the 100 columns used by the new UI tests the label `Tracker held: server reserve (next attempt in 30m 00s)` takes about 54 columns, so roughly 44 remain and the line ends inside the primary summary; no blocker, dimension, value or reevaluation time reaches the screen. I searched every non-test reader of `tracker.error`: monitor_ui.rs:63 (a flag), 399-424 (the row), 437 (the unconfirmed guard), monitor_department.rs:475 (`diagnostic_rows`, department views only, behind `e` and `d`) and monitor_main.rs:288 (the quit-time diagnostic for a Partial exit). `show_diagnostics` is read only in monitor_department.rs, the Scope view reads no `.error` of the tracker, and with a kept snapshot there is no scope error to show, so the coder's statement that the Scope view's unavailable text carries the detail does not hold for a kept snapshot. In the department views the row shows only the compact summary and the blockers appear after `e` then `d`. So for a lead on Tickets, Agents or Scope, which is the default and the user's view, every blocker of a held read is stored and none is displayed. The three new UI tests (monitor_ui.rs:1438, 1456, 1474) assert the label, `next attempt in`, `last snapshot` and the absence of rate-limit words, and never a blocker, so a truncation bug cannot fail them. The coder documented a one-line limit; that is a reason, not a defense, against a contract that all blockers are rendered. Confidence medium: the row and key paths are traced; whether the fix is a wrapped multi-line row, a details view or an ordering that keeps the decisive facts in view is a design choice for the coder. Fix: make every typed blocker (state, dimension, reported values) and the earliest reevaluation reachable on screen in the lead views at a realistic width, by a route the F1 help names, without moving the evidence hierarchy, the `v` selector or the F1 help, and add a rendering test that asserts a blocker of a multi-blocker decision is visible at 100 columns.

### FND-003 (medium) The remedy and wording follow the primary cause only

`Cause::of_decision` takes the primary state, which the SDK picks by precedence, with `ServerBackoff` highest and `EvidenceUnavailable` next (quota_decision.rs:27-36, 172-184). Quarantined legacy reservations always add an `EvidenceUnavailable` blocker (quota.rs:770-775). A decision can therefore have the primary state `ServerBackoff` and an `EvidenceUnavailable` blocker with `legacy_pending_reservations > 0`. For that decision `Cause::ServerBackoff.remedy()` is `None` (quota.rs:126-130) and `Notice::new` takes its remedy from the cause alone (quota.rs:174), so the reconcile action `Ask the quota owner to reconcile the quota evidence` is never shown; `waits()` is true, so the dashboard counts down to a retry that the quarantine will refuse again, and `decision_facts` prints `N pre-fence reservations pending reconciliation; not a server limit` (quota.rs:188-191) in the same detail whose summary says `Linear rate limited`. The first statement is true of the reservations and the second of the primary state, but nothing separates them, so a reader sees a rate limit that is and is not a server limit. This is the user's named case of quarantine with an actual explicit backoff and all blockers. Nothing here asks the consumer to rerank states: the SDK's primary state stays the lead, and the remedy for each reported blocker is derived from the blockers that are present. Confidence medium: the combination is reachable by the SDK's own derivation and no test builds it. Fix: derive the remedy lines from the set of reported blocker states (an `EvidenceUnavailable` blocker or pending reservations adds the reconcile action whatever the primary state), reword the reservation fact so it cannot be read as qualifying the primary cause, and bind the case with a fixture (see SR-1852 FND-002).

### FND-004 (low) The decision fixture misstates the SDK's derivation

The `decision` helper's docstring says `As the SDK derives them, its primary state is the first blocker's` (quota.rs:293-294) and the body sets `state` from `blockers.first()` (quota.rs:295-301). The SDK's `QuotaDecision::finish` takes `max_by_key(|state| state.precedence())` over the blockers (quota_decision.rs:172-178), so `decision(vec![local_window, server_backoff])` yields a primary `LocalWindowHeld` that the SDK cannot produce. The `simultaneous` fixture agrees with the SDK only because its first blocker happens to be the highest. Rust-style testing: a fixture must model the production invariant it stands for, or its assertions measure the helper. The same shape appears in the agent-msg table row, which builds `state: ServerReserveHeld` with an empty `blockers` list (tests.rs:1913-1930); that row only checks the reason mapping, so I note it and do not raise it separately. Confidence high. Fix: derive `state` in the helper from the highest-precedence blocker (or call the same ordering the SDK documents), correct the docstring, and keep the arbitrary numbers.

### FND-005 (low) A catch-all arm in the closed scenario fixture

`ScenarioSource::fetch_workspace` handles `scenario.decision()` first and then matches the rest with `Scenario::RateLimited`, `GraphQlFailure`, `LocalBudgetExhausted`, `LockRefused` and `_ => Ok(TrackerState::default())` (monitor_ops.rs:494-496). The `_` arm makes every variant not listed, including any variant added later, a success. SWM-184 FND-005 asked for a closed enum with an exhaustive match for this same fixture, and the Rust style rule is to avoid a catch-all that turns an unknown value into a valid one. Confidence high. Fix: list `Scenario::Succeeds` and the five decision-carrying variants explicitly, or return the decision error from one exhaustive match and drop the `Option` helper.

### FND-006 (low) The README sentence on held reads is too long

The added README text (crates/relay-tui/README.md:32-37) states the held-read label in one 35-word sentence with a semicolon: `A read the quota protection holds back is labeled by the typed state ix-board reports (local allocation, server reserve, quota evidence unavailable or quarantined, request not admissible); only an actual server backoff is labeled rate-limited.` The `r` sentence before it grew from 19 to 30 words. The parent's Vale run reports a new SentenceTooLong at line 34 in the added paragraph (the pre-existing ContrastFraming at line 30 is untouched and is not part of this finding). The repository docs rule is one fact per sentence under 30 words, and the `only ... is labeled` clause is the contrast framing the docs style avoids. Confidence high. Fix: one fact per sentence, for example the labels in one sentence and the rate-limit rule in another, in plain terms.
