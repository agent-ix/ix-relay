## Finding details

### FND-001 (medium) A successful read with unknown provenance is reported as a failed refresh

`TrackerRead::retained()` (monitor_ops.rs:76-79) is `self.freshness.as_ref().filter(|freshness| freshness.stale)`, and `apply_tracker_refresh` (monitor.rs:283-301) turns that into the notice `Linear refresh failed; showing the last snapshot`, sets `collection_failed = true` and, for the non-cooldown case, shows a `Tracker failed` evidence row with `Inspect source availability with ix-board, or open --report`. The doc comment says `stale` means the snapshot was retained because the latest refresh did not succeed. In the accepted SDK it does not only mean that. `ReadService::refresh` sets `stale: age.is_none()` on the success branch (lib.rs:969-978), with `failure_reason: Some("source fetch provenance unavailable")`, `rate_limit_until: None`, whenever `cache.source_started_at()` is `None` or the age is negative. `source_started_at` is `None` when the stored row has no read-start evidence, or its digest or timestamp no longer matches (cache.rs:169-180): a row written by an older ix-board before the evidence existed, or by `cache.replace` in the project-mutation paths. `fresh()` returns such a row for the ordinary 300-second TTL (cache.rs:17), so the first read after upgrading, or after an `ix-board` status or priority mutation, succeeds with `stale: true`. The SDK's own text says unknown provenance is never certified fresh (cache_status.rs:25), which is honest; the dashboard's reading of it is not: nothing failed, yet the user sees a failure row and a remedy for an unavailable source, and `quit_outcome` (monitor_main.rs:286-304) ends the session `Partial` with the failure text. The two cases are separable without reading `failure_reason`: on the success branch `stale` implies `age_seconds == None`, so `stale && age_seconds.is_some()` is certainly a failed refresh, while `stale && age_seconds.is_none()` is either a failed refresh with no provenance or a successful read with unknown provenance. The test `a_retained_snapshot_shows_the_failed_refresh_while_under_thirty_minutes_old` (monitor_ui.rs:1329) and the first test in monitor_ops.rs set `age_seconds: Some(..)` only, so no oracle covers the other half. Confidence high: traced end to end in the SDK source; I did not run it. Fix: classify with `age_seconds`; for the unknown-provenance case show neutral, true wording such as `Linear snapshot freshness unconfirmed; showing the last snapshot`, decide explicitly whether it sets `collection_failed`, keep the original `fetched_at`, correct the `retained` doc comment, and add a fixture with `stale: true, age_seconds: None, rate_limit_until: None` asserting the text does not say the refresh failed. No error-string parsing is needed.

### FND-002 (medium) `agent-msg work` accepts a retained snapshot of any age

The old pin's `workspace_snapshot()` was a fresh cache hit or `force_refresh_workspace()`, which called `cache.invalidate()` first and returned the fetch error (9c9e49f lib.rs:731-737, 862-868: `A failed fetch leaves the cache empty so later reads cannot use stale data`). The new `refresh()` returns `self.cache.last_complete()` on any failed refresh, with no age bound, as `Ok` and records the failure only in `cache_freshness()` (lib.rs:981-1009). `agent-msg work` calls `source_snapshot()` (work.rs:86-89: `service.workspace_snapshot()?`) and discards the service and its freshness, then uses the snapshot in two writes to the relay report: `work scope` resolves selectors to stable UUIDs with `resolve_work_scope` (work.rs:132) and `work focus` and `work agent` verify tickets with `verify_tickets` (work.rs:96, 145, 163). Consequence: with the new pin, a rate-limited or failing Linear makes these commands succeed against a snapshot that can be days old, with no message; a project or ticket deleted or moved since passes, and one created since is refused as not found, which is the stale-evidence failure the retained-snapshot work in relay-tui was written to avoid. The coder report lists agent-msg `work.rs` as an affected consumer and records no adaptation, and no test or spec statement covers it. Confidence medium: the code path is traced, but whether these commands should fail closed or warn is a product decision. Fix options: (a) read `service.cache_freshness()` after the read and return the error the old pin returned when the snapshot is retained after a failed refresh (use `age_seconds.is_some()` together with `stale` so unknown provenance is not refused, see FND-001); (b) use `workspace_snapshot_bounded` with a `ReadPolicy`, as the named-focus path does; or (c) keep reading the retained snapshot but print its source time and the failure on stderr. Add a test at a seam for whichever is chosen (the current function has no seam; see SR-1842 FND-003).

### FND-003 (low) Retained-snapshot notices bypass the shared classifiers

The Err arm builds its text with `monitor_ops::source_summary` and `source_diagnostic` (monitor.rs:309-317). The Ok(retained) arm writes its own strings inline (monitor.rs:293-299): `Linear rate limited; showing the last snapshot`, and `Linear refresh failed; showing the last snapshot` twice in one call, the second with the sentence `Inspect source availability with ix-board, or open --report` copied from the `TrackerReadFailed` arm of `source_diagnostic` (monitor_ops.rs:48). It also does not use the `Record::error(kind, message)` rendering that `source_diagnostic` applies, so a retained failure and a cold failure present differently in the same row. Rule: code-review duplication inside one repo, the same error string defined twice; and rust-review, one fact in one place. Search done: I read monitor.rs and monitor_ops.rs for the strings `Inspect source availability`, `Linear rate limited` and `showing the last snapshot`. Risk: a change to the remedy sentence or the classification has to be made in two modules. Fix: add the retained summary and diagnostic beside `source_summary` and `source_diagnostic` in monitor_ops.rs, reuse the remedy constant, and keep `apply_tracker_refresh` to selecting among them.

### FND-004 (low) A new field was added by hand-editing six test sites

`TrackerRead { snapshot, freshness }` (monitor_ops.rs:68-73) has one meaning for `freshness: None` (the service reported no provenance), and six tests now spell it out as a struct literal: monitor_main.rs:799, monitor_scale_tests.rs:299, monitor_scope_tests.rs:660, 1013 and 1028, and monitor_ui.rs:1311 (the `freshness: None` lines are 801, 301, 662, 1015, 1030 and 1313). The next field needs the same edit at all of them. Rust-review core check: check whether a new field requires hand-editing several sites. Fix: a `TrackerRead::unreported(snapshot)` constructor (or `From<TrackerState>`) used by those sites, so only the tests that mean a retained read build the full literal.

### FND-005 (low) The retained-snapshot test fixture hides later scenarios and uses an open-ended mode

`FlakySource` (monitor_ops.rs:327-345) selects its behavior from a shared `AtomicU8`: 0 succeeds, 1 is rate limited and `_` is a GraphQL failure, so any other value silently becomes a valid failure. Rust-style implementation: use a closed enum and an exhaustive match, never a catch-all that turns an unknown value into a valid one (the same rule SR-122 applied to a `u8` severity). The single test `a_snapshot_kept_after_a_failed_refresh_shows_the_failure_and_its_original_time` (356-449) runs a good read, a rate limit, a GraphQL failure on a warm app, the same failure on a cold app, a second rate limit and a recovery over one mutable `mode` and two apps, with asserts for each, so the first assertion that fails hides every later scenario and the failing line does not name the scenario. Fix: a small `enum Mode { Ok, RateLimited, Failed }` with an exhaustive match, and separate tests (retained with cooldown, retained without cooldown on a cold app, recovery) sharing a helper that builds the service.
