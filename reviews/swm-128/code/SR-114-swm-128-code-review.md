## Summary

Ticket: SWM-128. PR ix-relay#42, branch codex/swm-128-named-focus-definitions at immutable source 663425a106821d4b384666e7ee012b6410bf11f2 (base origin/main 9a804538). Code-review method with the Rust lane (rust-review and rust-style) folded into this one artifact. The change implements FR-061: durable named focus definitions, immutable revisions, one owner, compare-and-set (CAS) writes in Redis scripts, claim, forced claim, transfer, archive, bounded retention, adoption-pin primitives, and the `agent-msg focuses` command family, with the ix-board SDK pinned at 2d8c2a8d and called through ONE `canonicalize_named_selection_bounded` call.

The core is sound. Every restricted write is planned from one read and committed by one Lua script that re-compares the stored owner ID, epoch, revision, state, name mapping and the exact raw `meta` and `owner` bytes before its first write. The scripts never re-encode stored JSON, so unknown members survive. A claim compares the observed owner and never the caller. Unknown, partial and skipped registry reads are never counted as absent. The pin compare-and-delete, the retention limits and the reclamation triggers match FR-061. The CLI keeps stdout and stderr apart, prints one compact line, and refuses an invalid file before any credential is used. 13 findings: 1 high, 3 medium, 9 low. The medium and low findings are real but narrow. The one high is the code-review P0 duplication rule applied as written.

## Verdict

**FAIL** - one `high` finding (FND-001, a second statement in relay-core of the ix-board named-selection wire document, which ix-board owns). The code-review verdict rule makes any `high` a FAIL. The remaining defects (3 medium, 9 low) alone would be CONDITIONAL. No finding touches the CAS comparison logic, the liveness rule, the SDK budget use or the byte-identical-on-failure behavior, which held up under adversarial reading.

## Finding details

### FND-001 (high) Second statement of the ix-board named-selection wire document

Rule: code-review "Duplication and Vendoring", "another repo's values re-stated as a native const, enum, or type in code", and rust-style wire-and-persistence "Emit a named Serialize struct ... do not build the schema by inserting string keys into serde_json::Value". Search done: I searched the worktree and the accepted SDK sources for the kind spellings and the member keys. ix-board defines them as `NamedMember` (`#[serde(tag = "kind", rename_all = "snake_case")]`, variants Initiative, Project, Milestone with `project_id`, Issue), `NamedSelection` (`schema_version`, `team`, `include`, `exclude`), `NamedSelection::encode()` and `decode_named_selection()`. relay-core restates all of it: `MemberKind::wire` and `MemberKind::from_wire` (model.rs:125-144), `Member::wire_value` (model.rs:187-195), the `json!` selection in `Revision::build` (model.rs:434-439) and `parse_members` (model.rs:500-541). FR-061 Dependencies says the shared ix-board library "owns ... the wire type of a selection".

Concrete risk: two owners of the version 3 document shape. The relay emits keys in a different order than `NamedSelection::encode()` (the SDK states the same selection always gives the same bytes). The write-time `SelectionCheck` proves only that the SDK accepts what the relay built; it does not make the relay build what the SDK would. The read side (`members()`, `holds`, `show`) uses the relay's own parser, not the SDK decoder, so an SDK change that the decoder accepts and the relay parser does not (or the reverse) shows up as a wrong `holds` or an `undecodable` display, not as a loud failure. A guard over a copy does not make the copy acceptable (code-review text).

Fix: relay-core must not spell the document. Move construction and parsing behind the existing seam: the `SelectionCheck` trait becomes the codec (encode a normalized member list to the stored bytes, decode stored bytes to members), implemented in agent-msg with `NamedSelection::encode()` and `decode_named_selection()`. Delete `MemberKind::wire`/`from_wire`, `Member::wire_value` and `parse_members`. The relay-core integration tests then use a small test codec that is itself built on the SDK type, or the real `IxBoardCheck` through `relay_test_support`. Add a test that the stored selection bytes equal `NamedSelection::encode()` for the same members. If relay-core is allowed to depend on ix-board, storing `ix_board::NamedSelection` directly is the smaller change; the trade-off is a heavier dependency for relay-watcher, which the author avoided.

### FND-002 (medium) Member labels are dropped or are canonical IDs

FR-061: "Each member keeps a display-name label of at most 64 bytes ... used only for display." `file.rs:140-142` parses the file's optional `label`, requires a string, and discards it. `resolve.rs:173-188` sets every stored label to the canonical UUID, and `tests.rs:485` asserts `"the label is the canonical ID"`. `docs/cli-reference.md:611` documents `{"ref": "...", "label": "..."}` with no word that the label is ignored. The SDK limit (the bounded method returns only the canonical selection, and a second read is forbidden) explains why the relay cannot look a name up. It does not require ignoring the caller's own text. Risk: `show`, `list` and the later FR-063/FR-064 readers display a UUID where a human wrote `Completion`, `SWM-12` or a label; the 64-byte cut-on-boundary rule is never exercised in production; a caller who sets `label` is silently ignored. Fix: store the file's `label` when given, else the reference text when it is not the canonical ID (an exact name or an identifier is the display name the human wrote), else the canonical ID; keep labels out of identity (`holds` already does); add a test that a name reference and an explicit label survive `show --json`, and a 40-character multibyte label is cut to 64 bytes through the CLI path; document the rule.

### FND-003 (medium) Atomic-compare branches other than not_owner are not pinned by a deterministic test

The scripts compare, in order, name_moved, archived, owner_id, epoch, revision, in-script name_taken, then raw `meta` and `owner` (`retry`) (named_focus_scripts.rs:56-65 and the ARCHIVE, CLAIM and TRANSFER bodies). The one deterministic stale-plan test, `a_write_by_the_former_owner_after_a_transfer_is_refused_inside_the_atomic_operation` (tests/named_focus.rs:735), reaches only the owner_id branch; the assertions even accept either `not_owner` or `owner_epoch_conflict`. The concurrent update test (tests/named_focus.rs:324) lets either the plan phase or the script produce the loser's `revision_conflict`, so the script branch is not forced. Never executed by any test: the epoch-only mismatch (the same owner ID after A to B to A, epoch 3, a stale epoch-1 plan: the reason the epoch exists), `archived` returned by the script (a stale update plan committed after archive), `name_moved` for archive, claim and transfer, the in-script `name_taken`, and `Committed::Retry` (no test asserts `Retry`, and the re-plan loops in focus_update, focus_archive, focus_claim and focus_transfer are never driven). Risk: deleting or reordering any of those comparisons keeps the suite green while reopening the AC-9 lost-update window. Fix (test requests for the same coder): (1) plan an update and an archive as A at epoch 1, transfer A to B, transfer B back to A, commit the stale plans, expect `owner_epoch_conflict` and a byte-identical dump; (2) plan an update, archive, then commit the update plan, expect `archived`; (3) plan an update expecting revision 1, commit a different update, commit the stale plan, expect `revision_conflict` with `latest` 2; (4) resolve by name, rename and archive, then commit claim, transfer and archive plans built from the stale name, expect the name_moved refusal; (5) plan an update, change `owner` raw bytes without changing ID or epoch (for example a same-owner binding refresh), commit, expect `Committed::Retry` and an unchanged dump.

### FND-004 (medium) The production identity adapter is untested

`HerdrCaller::verify` (caller.rs:29-56) is the only place a Herdr observation becomes the `OwnerBinding` that every ownership comparison trusts: machine, native session ID, process ID and address, with `--session` mismatch refused as `invalid_argument`. All in-process tests use `FakeCaller`. The process tests in `focuses_cli.rs` install a fake `herdr` script, but no case reaches a write: the invalid-file case returns before `verify`, and the others are reads and usage errors. Risk: a wrong field mapping (for example the wrong machine or the address in the session slot) or a regression in `--lead`/`--session` handling breaks AC-6 and AC-9 identity only at runtime. The brief asks for per-session identity authority evidence from the real binding. Fix: add process tests with the existing fake herdr: (1) `focuses --json archive foc-00000000000000000000000000000001 --expected-revision 1` expects `not_found` (verify passed, then the store answered); (2) the same with `--session other` expects `invalid_argument` with field `session`; (3) with `HERDR_PANE_ID` unset and no `--lead`, expects `invalid_argument` with field `lead`; (4) with Redis, create a definition through the in-process harness owned by `terra/session-1`, then `archive` from the process with the fake herdr reporting session-1, and expect success, proving the owner ID produced by the real adapter matches the stored one.

### FND-005 (low) Catch-all mapping of SDK errors

`resolve.rs:107` (`_ => SourceReason::Failed`) and `resolve.rs:141` (`other => source_error(&other)`) map every other SDK error to a contract reason. The SDK `Error` is not `#[non_exhaustive]`, so an exhaustive match is possible and would force a decision when the pinned SDK adds a variant (rust-style implementation: never use `_ => ExistingValue` for an unknown domain value). Today `MissingProjectMilestone` (a snapshot whose issue points at a missing milestone), `ProjectNotFound`, `InvalidNamedSelection` and `BoundUnsupported` all read as `failed`; at least the first looks like `partial`. Tests cover four variants (`MissingApiKey`, `MissingWorkspaceData`, `BoundUnsupported` as the broken case, `ReadTimeout`). Fix: list every SDK variant, grouped, with no wildcard; add a table test that builds one value per group.

### FND-006 (low) Sanitize versus refuse

FR-061: a name "is sanitized as a single line (as a work-report field)". `checked_line` (model.rs:238-243) refuses any name, description or team that `text::sanitise_line` would change, with `invalid_argument`; `tests/named_focus.rs:282-322` asserts that a two-line description is refused. `sanitise_line` replaces newline, tab and unsafe characters with U+FFFD, so the work-report fields store the sanitized value. FR-061 sets no single-line rule for the description (only 512 bytes), so a description with a line break from a definition file is rejected without support in the requirement. Fix: sanitize the name as FR-061 states and store the result (the uniqueness key already derives from the stored name); for the description either sanitize as well or state the single-line rule in the docs and the FR; keep the refusal for an empty name. Judgement call: the author's strict reading is defensible, so confidence is low.

### FND-007 (low) name_moved is reported as name_taken

`refusal` maps the script's `name_moved` (the stored name mapping no longer points at the resolved ID) to `FocusError::NameTaken` with `holder: None` (named_focus.rs:145-152), whose message is "the name ... is already used by a non-archived definition of team ...". When the definition was only renamed or archived and nobody holds the old name, the message is false, and a caller keyed on `name_taken` will look for a holder that does not exist. The test (tests/named_focus.rs:460-482) only covers the case where another definition re-took the name. Fix: keep the code the contract allows but give the moved case its own message ("the name no longer resolves to this definition; reread") and the current holder when one exists; add the renamed-only and archived-only cases to the test.

### FND-008 (low) Stored field names differ from the FR record fields

FR-061 Ownership: the owner record has `binding` (`machine`, `native_session_id`, `process_id`, `address` and `verified_at`) and `change` (... and `at`); Adoption pins: the pin value has `incarnation`, `adopted_revision` and `pinned_at`. The code stores `verified_at_ms` (model.rs:578), `at_ms` (model.rs:648) and `pinned_at_ms` (model.rs:723, 734), and `show --json` prints them. The repo idiom for timestamps is the `_ms` suffix, which explains the choice, but the FR names the stored fields and FR-062 and the dashboard will read them across machines. NFR-004 (no compatibility layers) makes the cost of changing a name lowest now. Fix: rename the fields to the FR names (with an explicit unit documented), or amend the FR in a spec ticket before FR-062 starts.

### FND-009 (low) Live ignores an incomplete registry read

liveness.rs:111-117 returns `Live` for exactly one verified registration whether or not the registry read skipped records. FR-061 defines unknown as "every other case, including a failed or partial read, any skipped record". A skipped record can be a second registration for the same machine and session, which makes "exactly one" unprovable. The claim and pin-reclamation outcomes do not change (live and unknown both refuse a plain claim and keep a pin), but the owner state printed by `list` and `show`, and the `transfer` target check (focuses.rs:445), treat the target as live. Fix: when `complete` is false return `Unknown` even for a single verified registration, or document that a single match wins; add a test with one verified registration and a skipped record. Judgement call; confidence low.

### FND-010 (low) Timestamps are taken before the bounded read

`Env.now_ms` is read once (focuses.rs:186) and used for `written_at_ms`, the owner `verified_at_ms` and `at_ms`, `pinned_at_ms` and `archived_at_ms`. For `create` and `update` the atomic write happens after a read that may take up to the deadline (default 120 s, up to 600 s), so the stored write time is early by that amount. The 90-day retention arithmetic is not affected, but "the write time" in FR-061 is wrong by the read duration. Fix: take `now_ms` after the resolution and just before the planning step (a clock method on `Env`), and test it with the manual clock already in the harness.

### FND-011 (low) A print failure is reported as invalid_argument

`io_error` (focuses.rs:197) maps any stdout write error to `FocusError::invalid("output", ...)`. The Redis write has already committed, so the command exits 1 with `invalid_argument` after success, and a script that retries on any non-zero exit will then meet `name_taken` or `revision_conflict`. Fix: write the result before reporting an I/O failure as a plain message on stderr without a contract code, or treat a broken pipe as the other commands in this CLI do; add a test with a closed stdout.

### FND-012 (low) Script bounds and idiom

named_focus_scripts.rs hard-codes 4096 (create index limit and candidate field count, lines 132 and 149), 1024 (list index limit at line 216 and the field-name length in READ_ONE) and 65536 (field size), while `limits.rs` defines `MAX_INDEX_ENTRIES = 1024` and `MAX_FIELD_BYTES = 64 * 1024`, and only `MAX_FIELDS` is substituted. A store with 1025 to 4096 index entries lets `create` run and makes `list` and the removal pre-read refuse. `focus_script` builds a new `redis::Script` from a freshly concatenated `String` on every call (named_focus.rs:295; named_focus_scripts.rs `guarded`, `plain`, `compose`). Every existing script in the crate is a `store/lua/*.lua` file held in a `LazyLock` (inflight.rs:117-140, stranded.rs:18). rust-style: keep a fact in one place. Fix: substitute every bound from `limits.rs`, and move the bodies to `lua/focus_*.lua` with one `LazyLock<redis::Script>` each.

### FND-013 (low) CLI reference gaps
