# ix-relay

A message bus for team leads, and an inbox for their escalations. Leads on node-a, node-b
and hub send each other messages without a human relaying them. Only leads use it;
subagents use their harness's own messaging.

The bus is its own Redis, relay-redis, in the hub's Kubernetes cluster (namespace
`relay`), reached by every machine, the hub included, at `10.99.0.1:6380` over
WireGuard, each machine as its own Redis user. See "Transport".

## Transport

```
peer ──┐                                    hub
       ├─ WireGuard (UDP 51820) ──> wg0 10.99.0.1:6380 ── relay-redis-proxy ──> relay-redis
peer ──┘                                     (socket unit)    (NodePort 31379 in kind)
```

- **relay-redis** is the chart in `helm/`, deployed with `ix local up ix-relay
  --from-source`. AOF on a PVC. Its `default` user is off; each machine has an
  ACL user limited to `ixr:*` keys and `+@all -@admin -@dangerous`. The
  `admin` user's password is generated by ix-cli into the `relay-redis-admin`
  Secret and only ever used inside the pod. It shares nothing with
  `platform/redis`, which stays cluster-internal.
- **WireGuard** (`wg0`, `10.99.0.0/24`): the hub is `10.99.0.1`, each
  other machine a peer at `10.99.0.x`. For now the hub accepts WireGuard only from
  the LAN; off-LAN access (a DNS name and a router forward) is AGE-2068.
  WireGuard answers nothing to a packet without a peer key, keeps no connection
  to drop, and resumes by itself after sleep or a network change.
- **Firewall on the hub**: `wg0` carries its own nftables table (`inet ixrelay`,
  `/etc/wireguard/ixrelay.nft`), loaded and removed by `wg-quick` with the
  interface: over `wg0`, peers reach `10.99.0.1:6380` and nothing else, and
  WireGuard's UDP port takes only the LAN. It filters nothing else on the hub and
  does not need ufw.
- **The forwarder** (`deploy/relay-redis-proxy.{socket,service}`, a user unit on
  the hub) is a plain TCP relay from `10.99.0.1:6380` to relay-redis's NodePort. It
  replaces `kubectl port-forward` for the relay.

`scripts/relay-admin` runs on the hub and does all of it:

```bash
scripts/relay-admin hub-init                  # once: wg0 + its firewall (sudo; needs wireguard-tools, nftables)
scripts/relay-admin add-user <hub>            # the hub's own ACL user; prints its bus url
scripts/relay-admin add-peer <machine> <key>  # peer + ACL user; prints its wg config and url
scripts/relay-admin remove-peer <machine>
scripts/relay-admin migrate                   # copy the old bus's keys (see "Moving from the old bus")
scripts/relay-admin status
```

### Adding a machine

Each machine makes its own key; only the public key travels. Make the key on
the machine it belongs to: a key made elsewhere means copying a private key.

1. **Make the key, on the machine.**
   - Linux:

     ```bash
     sudo apt install wireguard-tools
     sudo sh -c 'umask 077; wg genkey > /etc/wireguard/relay.key; wg pubkey < /etc/wireguard/relay.key'
     ```

     The last line prints the public key (44 characters ending in `=`).
   - macOS: install the WireGuard app (Mac App Store), **Add Empty Tunnel…**,
     name it `relay`, save it without activating, and copy its **Public key**.
     The app keeps the private key.
2. **Add the peer, on the hub** (quote the key):
   `scripts/relay-admin add-peer <machine> '<public key>'`. It creates the
   machine's ACL user, adds the WireGuard peer, and prints the machine's bus URL
   and its WireGuard setup: a ready-to-run command for Linux, the lines to add
   for the macOS app, and the check. The URL holds the machine's password:
   keep it off the bus and out of tickets. A key typed wrong is refused before
   anything changes; a key already added is refused as a duplicate (see
   `remove-peer`).
3. **Install the tunnel, on the machine.** Linux: run the printed command, which
   writes `/etc/wireguard/relay.conf` from `relay.key` and enables
   `wg-quick@relay`. macOS: in the `relay` tunnel keep the generated
   `PrivateKey`, add the printed lines, save, **Activate**, and turn on
   **On-Demand** under Edit.
4. **Check, on the machine:** `nc -z -w3 10.99.0.1 6380 && echo bus-reachable`.
   `ping` will not answer: over `wg0` the hub accepts only TCP 6380.
5. **Join the bus, on the machine:** set `url = "<printed url>"` in
   `~/.ix/relay/config.toml`, restart the watcher (`systemctl --user restart
   relay-watcher`, or `launchctl kickstart -k gui/$(id -u)/com.agent-ix.relay-watcher`),
   and run `agent-msg doctor`: `redis: ... answers` means it is on the bus. A
   failure names what to check: the password, the hub's forwarder, relay-redis
   behind it, the WireGuard handshake (`wg show`), or WireGuard not being up.

Lost the printed URL? `scripts/relay-admin add-user <machine>` on the hub issues a
new password and prints the URL again (the old one stops working).

### Moving the v3 namespace between Redis servers

This transports an existing v3 deployment only. For a pre-0.3 identity upgrade,
use the coordinated namespace cutover below; never import old identities.

Until every machine has joined, the old bus (`platform/redis`, reached through
SSH tunnels and the hub's `redis-port-forward.service`) keeps working. The move:

1. Every machine passes step 4 above.
2. Each machine does step 5, one after another. A message sent between a
   machine that has moved and one that has not yet lands on the other bus.
3. On the hub, once all have moved: `scripts/relay-admin migrate` copies the old
   bus's `ixr:v3:*` keys (queued mail, session registrations, escalations) with
   their TTLs. A key relay-redis already has is kept, not overwritten; the old
   copies are left in place.
4. Retire the old path: the SSH tunnel units on the other machines, and on the hub
   `systemctl --user disable --now redis-port-forward.service` once nothing
   else uses `127.0.0.1:6379` (`ss -tn state established '( dport = :6379 )'`).
   Then delete the old `ixr:v3:*` keys from `platform/redis`.

## Configuration

`agent-msg` and `relay-watcher` both read machine-level settings from
`~/.ix/relay/config.toml`, same as every other agent-ix tool keeps its
settings under `~/.ix/<tool>/`. Nothing here is required — a missing file
means the compiled-in defaults — but it's the normal place to fix a machine's
Redis URL, key prefix or (once and for all, per machine) its name on the bus:

```toml
url = "redis://node-b:<password>@10.99.0.1:6380"   # from `relay-admin add-peer`; see "Transport"
machine = "node-b"          # fixes hostname casing (node-b reports "Node-B")
prefix = "ixr:"
human = "operator"             # who escalate/resolve notify/sign as

[watcher]
interval_secs = 2
# otlp_endpoint = "http://collector:4318"   # push OTLP metrics here; unset = send nothing
# otlp_headers = "Authorization=Bearer%20token"   # optional, name=value,name=value
# otlp_interval_secs = 30   # 5 to 3600; see "Metrics"
delivery = "herdr"          # or "socket": see "Delivery through Claude Code's inbox socket"
```

Every key is optional; only set the ones a machine needs to override. Each
one resolves **flag > env > file > default** — a `--url` flag beats
`IX_RELAY_URL`, which beats `config.toml`, which beats the compiled-in
default. A missing file is just the defaults; a malformed one is an error
naming the file, line and column (`agent-msg hook` reports it on stderr and
still exits 0, so a typo in the file never breaks a lead's turn — every other
command exits 1). `IX_RELAY_CONFIG` overrides the file's path, for tests.

`AGENT_MSG_NAME` is preserved as session environment metadata and does not
participate in identity or routing.

## agent-msg

```
agent-msg send <address|all> "<text>"   # signed as you (see "Automatic bus names"); prints who it queued for and the recipient's state
agent-msg inbox                      # print and remove your pending messages
agent-msg who                        # registered leads
agent-msg find [<query>]             # discover live leads by address, label, session or pane
agent-msg log [--since 1h]           # history
agent-msg doctor [--json] [--strict] # is the relay healthy? read-only; exits 1 on a failure (--strict: on a warning too)
agent-msg register [--kind manual]   # register by hand; hooks do this on session start
agent-msg whoami [--json]            # print this session's verified address
agent-msg hook <claude|codex>        # hook handler, reads hook JSON on stdin
```

| Env | Meaning | Default |
|---|---|---|
| `AGENT_MSG_NAME` | preserved environment metadata; ignored for identity and routing | — |
| `IX_RELAY_URL` | Redis URL; see "Configuration" | `redis://127.0.0.1:6379` |
| `IX_RELAY_PREFIX` | Redis key prefix; see "Configuration" | `ixr:v3:` |
| `IX_RELAY_MACHINE` | machine name recorded at registration; see "Configuration" | hostname |

A send to one lead prints its state after `queued for`, for you only (nothing is added to
the recipient's inbox or context): `queued for hub:EA:code (watcher heartbeat from hub (last
tick 3s ago), 1 waiting)`, or `(no watcher heartbeat from hub, 1 waiting)` when no heartbeat is
live for that machine (a watcher older than the heartbeat has none). The state is one extra request with one reply, bounded at a quarter of a second
in all; when Redis is slow you get the plain `queued for <address>`. A machine name that is not
hostname-shaped (letters, digits, `.`, `-`, `_`, at most 32) is never printed.

### Location identities and automatic enrollment

Recipient resolution uses ix-relay's leased Redis directory first. Each watcher
publishes a complete verified observation from its own local Herdr, including
empty and ambiguous states. A sender needs no outbound SSH or remote Herdr
machine profiles. Cold remote resolution requests a destination-watcher
refresh through Redis and waits up to 60 seconds; local Herdr is a fallback
for cold local recovery. Enqueue atomically checks the publication lease and
fence again. Stale durable registrations do not establish address ownership.

Successful topology observations receive ordered Redis fences before reading
Herdr and publish with a 90-second Redis-clock lease, normally refreshed every
30 seconds. Failed or incomplete reads cannot renew that lease. Delayed or
replayed observations cannot restore superseded ownership. Session queues
survive renames, moves, closure, and address reuse; routing never transfers old
mail to the new session occupying a pane. These guarantees and their limits
are modeled in [the directory state model](spec/reviews/relay-directory-state-model.md).

Every lead is identified by `server:workspace:tab`. The tab is always included.
Send a full address, `:workspace:tab` on your verified server, or `:tab` in your
verified workspace. The owning watcher checks live Herdr session associations and
registers an absent recipient automatically, publishing current ownership
through the relay. A stale registry record never supplies caller identity.

Renames and moves change the visible address while the genuine session keeps
its immutable queue identity. Agent nicknames, `/rename` titles, old aliases,
bare names, raw pane IDs, omitted tabs, and pane suffixes do not route messages.
Multiple live sessions sharing a tab are rejected. Label text is preserved,
with case-insensitive matching; quote addresses containing spaces.

`AGENT_MSG_NAME` is preserved but ignored for identity. `whoami`, `who`,
`find`, and message signatures show addresses. Hooks require the genuine
harness session to match Herdr. Interactive Codex starts/resumes use
`scripts/codex-herdr-launcher.py`, installed as `~/.local/bin/codex`, which
adds `--no-daemon` in Herdr. This prevents the shared daemon's inherited pane
from replacing the terminal's real startup context. Herdr's SessionStart
helper runs before relay registration. Existing sessions need a genuine
startup/resume event; never invent a session ID or guess a nearby pane.

Version 0.3 uses the `ixr:v3:` namespace. Stage matching binaries, launcher,
and plugin guidance on every server before changing the configured prefix.
Pause watchers during the coordinated cutover, archive the prior namespace,
then start the new watchers with socket delivery enabled. Keep the prior keys
until their owning sessions are verified; never assign backlog by nickname.

Archive the old namespace without deleting any source keys:

```bash
python3 scripts/archive-relay-namespace.py --prefix ixr: --output /private/tmp/ix-relay-v2-archive.jsonl
```

The archive contains binary-safe Redis DUMP payloads, keys, capture times and
remaining TTLs, stored with mode 0600. It excludes `ixr:v3:` and never imports
aliases. Pause old writers first for a stable cutover snapshot; a SCAN archive
made while writers are active is explicitly marked as non-atomic.

### How a message reaches a lead

| Lead state | Delivered by |
|---|---|
| Working | `PostToolUse` hook (mid-turn) or `Stop` hook (blocks the turn end) |
| Starting | `SessionStart` hook delivers the backlog |
| Idle or done | `relay-watcher` wakes it with `herdr agent prompt` |
| Blocked on an approval dialog | left queued; `relay-watcher` notifies the operator once per episode |

A delivery removes the message from the inbox in one Redis command, so a message is
never delivered twice. `agent-msg log` keeps the history. The hook never fails the
agent: it reads stdin inside its deadline too (a harness whose stdin yields no complete payload costs at most about 300 ms of silence, or 900 ms in all while bytes keep arriving, and the hook then records `decode`/`stdin_timeout`, pops nothing and exits 0; a `UserPromptSubmit` payload that completes after its own 300 ms is recorded as `budget`/`budget_exhausted` instead; the read ends at the first JSON object, so the pipe need not close; input over 8 MiB is a recorded `decode`/`too_large`), and if Redis can't be reached it gives up within its budget (300 ms at `UserPromptSubmit`, 900 ms at `PostToolUse` and `Stop`, which exist to deliver mail) and exits 0. A pop is issued only when twice the measured round trip plus 20 ms is left, so a slow tunnel defers or records a skipped pop instead of losing mail; `UserPromptSubmit` delivers over links up to about 55 ms, `PostToolUse` and `Stop` up to about 290 ms.

Failures it swallows are not silent: each appends one typed record (stage and a
stable error code, never message text, and an id minted when it is appended) to
`spool/hook.jsonl` beside `config.toml`, bounded to 256 KiB, and the next hook that reaches
Redis ships them to the capped `health:hooks` stream and removes them from the file by id. Each
ship is one atomic request that skips ids the bus already recorded as shipped (the last 24 hours,
at most 2,000), so a record reaches the stream once however flushes overlap or retry, and
`doctor` and the metrics count an id once. A hook with less
budget left than twice the round trip it measured plus 20 ms (never under 30 ms)
skips the pop instead of risking a reply that arrives after the timeout, and a popped batch that cannot be printed is put back at the
front of the inbox (or left in flight, and kept in the spool record, if even that fails).

### Delivery is at-least-once

For the hook and the watcher. A pop does not remove a batch, it moves it into that
lead's in-flight record (`inflight:<lead>`) in the same Redis script. The hook
acknowledges right after its output was written and flushed ("delivered" means
written to the pipe: what the harness does with the bytes afterwards is beyond the
hook); the watcher acknowledges when `herdr agent prompt` reports success. A batch
that is never acknowledged (a hook killed after its pop, a watcher that crashed
before prompting, a prompt whose outcome is unknown) returns to the front of the
inbox, in order, when its lease runs out: 20 s for a hook, 60 s for the watcher, on
Redis's clock. Each batch returns on its own lease, so a redelivered batch is marked
and may arrive after newer mail. The hook
reaps its own lead's due batches inside its pop; the watcher reaps every registered
lead at start-up and on each sweep. A crash after delivery and before the
acknowledgement delivers the batch twice, so a redelivered message is signed
`[ix-relay] from <sender> (redelivered): ...`; its count travels with the stored
entry as trailing spaces after its JSON, so an identical message sent afresh starts
at zero. After three redeliveries a message moves to `deadletter:<lead>` (newest
1,000 kept) and `agent-msg inbox --dead` lists it.

A lead may have at most 16 unacknowledged batches and 1 MiB of them in flight; a pop
that would exceed either while something is in flight takes nothing (a hook records it, the watcher logs "in-flight
cap reached" once per episode) until a lease frees room. `agent-msg inbox --in-flight`
lists every lead with in-flight entries or dead letters, registered or not, scanning at
most 1,000 keys of each kind. Every script checks the type of the keys it writes
before its first write and writes each move's destination before deleting its source.

The opencode plugin delivers through `agent-msg inbox --json`, which pops outright and
stays at-most-once until it gets a claim and an acknowledgement (AGE-2051).
`agent-msg inbox` as a human's read also pops and clears without a lease.

### Hook round trips

Over a network link a hook costs its number of sequential Redis requests times the
round trip. A pipeline counts as one. Counted with a proxy between the real binary
and a real Redis (`crates/agent-msg/tests/round_trips.rs` pins the "after" column):

| Hook path | Sequential Redis requests |
|---|---|
| Cached prompt or tool hook, empty inbox | 2 |
| Cached prompt or tool hook, one delivered batch | 4 |

The session probe and inbox pop each cost one request. A nonempty pop adds the
address read and acknowledgement. Startup verifies the genuine session through
Herdr and atomically registers its queue and session cache. Cached hooks never
replace verified placement with an empty registration. Expired in-flight batches
return to the inbox in the pop request.

## Escalations

A lead escalates only for a decision that's genuinely the operator's to make — not
one it's equipped to make itself. It states the options it sees and its own
recommendation, then keeps working on other things while it waits; the operator
investigates and resolves it whenever they get to it. Escalations are stored in
Redis, separately from the message inbox, with a status (`waiting` →
`investigating` → `resolved`) that only ever moves forward.

```
agent-msg escalate <ticket> --context <text> --option <text>... --recommend <text>
                                      # file one; prints its id (e.g. e7). Refused if
                                      # your genuine session is not registered, or has
                                      # no recorded session id. Also notifies the
                                      # configured human with a short pointer, never
                                      # the context/options/recommendation themselves
agent-msg escalations [--status waiting|investigating|resolved]
                                      # list them (every state by default)
agent-msg investigate <id> [--fresh] # The operator: open a Claude session on the lead's
                                      # machine, in its cwd — forked from the lead's
                                      # own session (needs a claude-kind lead), or
                                      # fresh with a fixed prompt pointing at
                                      # `escalation show`
agent-msg resolve <id> "<decision>"  # The operator: record the decision, send it to the
                                      # lead over the bus, and post it as a comment
                                      # on the Linear ticket
agent-msg escalation show <id>       # print one escalation's full detail: ticket,
                                      # lead, machine, cwd, kind, status, context,
                                      # options, recommendation, decision
agent-msg escalation post-linear <id>
                                      # retry posting a resolved escalation's
                                      # decision to Linear, if resolve's own post failed
```

**No escalation text (context, options, recommendation) ever crosses a shell
or a terminal's escape-sequence interpreter.** `investigate`'s fresh-session
prompt is a fixed string built only from the escalation id, the lead's name
and the ticket — never the lead-supplied text, which the fresh session reads
back itself with `agent-msg escalation show <id>`. `Relay::escalate` also
rejects control characters (other than `\n`/`\t`) in that text as defense in
depth.

`escalate` and `resolve` sign the human side as `operator` by default;
`~/.ix/relay/config.toml`'s `human` key (or `IX_RELAY_HUMAN`, or `--human`)
overrides it — see "Configuration". `resolve` posts to Linear through the
`linear` CLI on whichever machine runs `resolve` — normally node-a, where
the operator works. If that post fails, the escalation still moves to `resolved` and
the lead is still notified; `resolve` prints the failure and the
`agent-msg escalation post-linear <id>` command to retry it. `investigate`'s
fork path only works for a `claude`-kind lead (`--resume <sid> --fork-session`
is Claude Code-specific); any other kind needs `--fresh`.

## relay-watcher

One process per machine. It wakes when a message is sent (it blocks on the message
log stream that every send appends to, so there is no poll delay), then reads the
leads registered on this machine (same machine name `agent-msg` resolves — see
"Configuration") with a known herdr pane and a non-empty inbox. In herdr mode,
it asks herdr for their state, and:

- idle or done: pops the inbox and types the messages in with `herdr agent prompt`,
  rechecking `state_change_seq` right before typing so a lead that just started a
  turn is left for its own hook instead;
- working: left alone, the hook delivers when it next runs;
- blocked on an approval or question dialog: left queued, and `herdr notification
  show` fires once per blocked episode;
- pane has no agent, or a herdr call errors: logged to stderr and skipped.

A lead left for its hook or a dialog still has mail queued and nothing new coming, so
it is looked at again every `interval_secs` (default 2 s). A backup sweep every 15 s
looks at every local lead whatever woke or did not wake the watcher, so a wake lost to
a dropped connection or a restarted Redis costs seconds, not a message. An idle
watcher makes no herdr call and no Redis request but the blocked wait (re-issued every 5 s, so a dead tunnel is noticed within 6 s) and the sweep (`--sweep-secs`, default 15). Messages sent to other machines cost no herdr call here.
Typing a batch in goes through a small `Deliverer` trait; `herdr agent prompt` is the
default implementation, and Claude Code's inbox socket is an opt-in second one (next
section).

### Mail stranded in a session's inbox

A queue belongs to a session, and an address names a place. When a session ends or is
replaced in its pane, mail sent to the address before the change waits in an inbox nobody
will pop. Once per place refresh, from the `agent list` it already reads, the watcher looks
at each local registration with queued mail whose pane no longer hosts its session. If
exactly one other registration holds the same `server:workspace:tab` address and herdr
verifies its session in its pane, the queued mail moves to that registration, in order and
before its own mail, and each moved message tells its reader, on its signed first line, that
it was sent to a prior session of the address (`[ix-relay] from <sender> (sent <UTC time> to
a prior session of this address): ...`). If no registration holds the address and the
registration is a day old, the mail is moved to the dead-letter list and the registration is
pruned, so mail never waits forever for a session that never registers. Anything uncertain
(herdr silent or unreadable, two registrations at the address, a pane that still hosts its
session) moves nothing.

### Delivery through Claude Code's inbox socket

**Opt-in, off by default.** With `[watcher] delivery = "socket"` the watcher posts a
batch to the inbox socket Claude Code binds for the lead's session, so it arrives as
Claude Code's own cross-session message (a dim `Message from @name` line) instead of
typed text, with no Stop-hook error label. Anything else (`"herdr"`, or no setting)
changes nothing. Nothing here is on unless you turn it on.

How it behaves:

- Socket delivery works while Claude is busy, idle, or blocked without first
  reading herdr's pane state. In socket mode,
  Claude hooks maintain registration but leave mail for the watcher. If the watcher
  is stopped, mail remains queued until it returns.
- It finds the socket by the lead's session id in Claude Code's session registry
  (`~/.claude/sessions`, read only), every time, and only trusts a record whose process
  is alive, has the recorded start time and pid namespace, and reports `peerProtocol`
  1 and version 2.1.224 or later. The socket is Claude Code's own; the watcher only
  binds its reply socket at `$XDG_RUNTIME_DIR/cc-socks/<pid>.sock` on Linux, or
  `/tmp/cc-socks/<pid>.sock` on macOS (an explicit `XDG_RUNTIME_DIR` overrides
  the reply directory). On macOS process identity matches Claude
  Code’s UTC `ps -o lstart=` timestamp and `darwin` pid domain; Linux uses `/proc`.
- herdr stays the fallback: no live socket record, a refused connection, a reply
  socket that is not bound yet (it is bound later, with backoff), or a receipt saying the
  message was refused or dropped can fall back to `herdr agent prompt` for that batch.
  The fallback requires two reads confirming the same registered session, regardless
  of pane activity. If identity cannot be confirmed, including when there is no session
  id, the batch returns to the inbox.
- A batch is acknowledged only when its message id shows in the lead's transcript
  (`~/.claude/projects/.../<session>.jsonl`, read only, at its end). The watcher waits up
  to 3 s for that, and posts a batch only when the tick's 8 s socket budget still covers
  the worst case of a post, 7 s (a 2 s connect, a 2 s write and the 3 s wait); otherwise the
  batch is put back for the next tick, unposted, with no notification. Leads are looked at
  in a rotating order, so a lead behind slow ones is reached within as many ticks as there
  are leads. The transcript baseline is taken before the line is written, so a receiver
  that records the message at once is never missed. If the wait ends with no receipt
  and no transcript line, the batch stays in flight with its lease renewed. Later mail
  still uses sockets. Pending consumption survives a watcher restart; after 30 minutes
  without confirmation it is dead-lettered as `consumption_expired`, without reposting.
  A pending message appears as `socket_pending` in doctor, distinct from an approval hold.
- Receipts are read for the life of the watcher and matched by the exact status:
  `delivered` (the user approved a held message) lets the transcript acknowledge it,
  `denied` dead-letters that batch (its reason is in `doctor`, not on the entry), a hold
  timeout puts it back unmarked.
- `agent-msg doctor` reports, per watcher (`state/socket/socket-<pid>.json`), the mode, the
  sockets resolved, the leads held and a reply socket that is not bound, as `ok`, `warn`
  or `unknown`, never as a failure. The reply socket is removed on exit and on SIGTERM
  or SIGINT (handled with the safe `signal_hook::flag`); after a SIGKILL it is removed at
  the next start.
- While Claude Code holds a message behind an approval prompt the watcher renews the
  batch's lease every tick, so it stays in flight (the reaper, the lead's own hook and
  the watcher leave it alone) and a late approval or denial finds it. After 30 minutes
  unanswered it is dead-lettered with the reason `hold_expired` and one notification; a
  denial dead-letters it (reason `denied`). Dead letters do not carry a reason, so
  `doctor` shows the reasons, from the watcher's status file. A batch held across a
  restart is restored from that file; if the file is lost, or the watcher or the bus is
  down for more than the 120 s lease, it degrades to at-least-once redelivery (the lead's
  own hook may deliver it while the socket copy is still held, and the lead stays marked
  held for the quiet period). While a batch is held, newer mail is delivered first by the
  hook, and after the quiet period the watcher posts again behind the same prompt, so a
  late approval can deliver older mail after newer. A message Claude Code reported
  delivered whose transcript line never shows is acknowledged after 5 minutes
  (`delivered_unconfirmed` in `doctor`). A decision about a batch
  (acknowledge, put back, dead-letter) is kept until its write to the bus succeeds: while
  the write fails the batch is renewed and the write retried after a growing wait (5 s up to
  5 minutes), and after five failures one notification and a `settlement_failed` note are
  raised; it is never given up on, and the message is never posted again meanwhile. The
  approved state and its time are kept in the status file, so a restart inside the 5-minute
  grace continues it. The status files live in their own directory, `state/socket`, created 0700 in one step; an
  existing directory that is open, a symlink or another user's is not used, read or repaired,
  and a symlinked or foreign file is not read; each file is created 0600, and the dead-letter
  reasons in it age out after 24 hours. Decisions still owed a write are kept in it too, so a
  restart neither loses an acknowledgement nor turns a denial into `hold_expired`. A write of
  one line is given 2 s in total, however slowly the receiver reads.

**Requirement for bypass-mode leads.** A Claude Code session in bypass mode holds every
message from another session behind a Deny/Deliver prompt unless
`crossSessionInbound: "accept"` is set in its user settings, `--settings` or managed
settings (plugins and project settings cannot set it). The watcher does not set it and
never writes any Claude Code file. When a lead's mail is held, the batch stays in
flight (herdr is deliberately not tried: it would type the batch twice and leave the
prompt up), no more mail is popped for that lead for ten minutes (it stays in the
inbox, not in flight, so it cannot expire and dead-letter), the operator gets one notification
per episode, and `doctor` warns. The two ways
out are setting `crossSessionInbound` to `accept` for that lead, or `delivery =
"herdr"`. Whether to make that setting standard is an open owner decision, which is
why the socket is off by default.

**Risk: the wire format is undocumented.** Claude Code documents that the socket exists
but not the line the watcher posts, how a session's socket is found, or its receipts;
they were measured on Claude Code 2.1.283 (FR-044) and can change in any release. That
is why an unknown `peerProtocol` or version is refused and herdr is always behind it.
Linux only (`/proc`); on other systems every batch goes to herdr. Only Claude Code leads
have such a socket: a Codex or opencode lead has no record, so its batches go to herdr.

```
relay-watcher                          # loop forever: wake on sends, retry a lead with mail every 2s
relay-watcher --interval-secs 5        # retry a lead with mail less often
relay-watcher --once                   # one sweep, then exit (manual checks, tests)
```

|---|---|---|
| `IX_RELAY_URL` | Redis URL; see "Configuration" | `redis://127.0.0.1:6379` |
| `IX_RELAY_PREFIX` | Redis key prefix; see "Configuration" | `ixr:v3:` |

### Wire formats

Claude Code's cross-session formats (the inbox-socket line and its wrapper, the receipts,
`~/.claude/sessions/<pid>.json`, and the transcript's `origin.msg_id`) are not documented
and can change in any release. They are typed in one crate, `crates/claude-wire`, which does
no I/O, and every format has a drift signal so a change is detected, not silently absorbed:

- Parsing is total. A reply-socket line that is JSON in an unknown shape, one that is not
  JSON, and a receipt with an unknown status are **counted against the Claude Code version**
  they came from, in hourly buckets that age out after 24 hours (in
  `~/.ix/relay/state/socket/socket-<pid>.json`, one log line for the first of each kind and
  version), with the last offending line's `type` and `action` (cut to 64 characters, never a
  body or a path), and shown by `agent-msg doctor` as a `socket_wire_drift` warning per
  version. Delivery is otherwise unchanged. For each version `doctor` also says whether it is
  working (acknowledged deliveries, no drift in the window), in drift, or just listed.
- A transcript line that names a message id without a structured `origin.msg_id` is evidence
  Claude Code received it: the batch is acknowledged as received but unconfirmed (a drift
  note, no herdr fallback, no redelivery) and shows as `socket_transcript_shape_unrecognised`.
  Busy consumption on Claude Code 2.1.302 is recognized through the typed
  `attachment.origin.msg_id` of a peer `queued_command`, captured during titan's
  live acceptance. Queue-operation enqueue/remove entries alone are not that acknowledgement.
  A lead that
  reads `socket-<pid>.json` (it lists held message ids) can cause a false drift count.
- The formats were captured on Claude Code 2.1.283 (`claude_wire::CAPTURED_ON`); `doctor`
  prints that version as what the fixtures describe, but whether another version works is
  told by what the watcher observes of it (the drift above), not by comparing versions.
  Contract fixtures in `crates/claude-wire/fixtures/claude-2.1.283/` are marked in
  their `MANIFEST` as `captured` (unedited live bytes), `captured-shape` (a live shape or our
  own golden with placeholder values), `derived-from-program-text` (read from the installed
  program, never seen live) or `synthetic` (a drift sample of our own).

The inventory of every external format, its owner and its drift signal is in
[spec section 15](./spec/spec.md), and the requirement is
[FR-046](./spec/functional/FR-046-claude-code-formats-are-typed-and-drift-is-detected.md).

### Metrics

Claude Code's OpenTelemetry metrics are labelled with herdr's stable pane, tab and
workspace ids, which say nothing about who is who. With an OTLP endpoint configured, the
watcher **pushes** metrics to it (OTLP/HTTP), so a dashboard can join the ids to names and
history keeps the name a pane had at the time, and it pushes a few relay health series
besides. With no endpoint (the default) it sends nothing, and it never binds a listening
socket either way.

```toml
[watcher]
otlp_endpoint = "http://collector:4318"     # /v1/metrics is appended
otlp_headers = "Authorization=Bearer%20token"
otlp_interval_secs = 30
```

or the relay's own variables `IX_RELAY_WATCHER_OTLP_ENDPOINT`, `IX_RELAY_WATCHER_OTLP_HEADERS` and
`IX_RELAY_WATCHER_OTLP_INTERVAL_SECS` (5 to 3600 seconds; anything else is refused).

**Precedence.** The relay's own settings come first, and headers always come from the
same tier as the endpoint, so credentials meant for one collector are never sent to
another:

| Endpoint from | Headers from |
|---|---|
| `IX_RELAY_WATCHER_OTLP_ENDPOINT` | `IX_RELAY_WATCHER_OTLP_HEADERS` |
| `[watcher] otlp_endpoint` (when the variable above is unset) | `[watcher] otlp_headers` |
| `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` (used as written), else `OTEL_EXPORTER_OTLP_ENDPOINT` (`/v1/metrics` appended), only when neither of the above is set | `OTEL_EXPORTER_OTLP_HEADERS` |
| none: nothing is sent | none |

The generic `OTEL_*` variables belong to other emitters on the same host (Claude Code
sets them for its own telemetry), so they are honoured only as that last fallback, only
for an `http://` endpoint, and only when `OTEL_EXPORTER_OTLP_(METRICS_)PROTOCOL` is unset
or `http/json`. Otherwise (an `https://` endpoint, `grpc` or `http/protobuf`, a bare host,
malformed headers) they are **ignored**: the watcher does not exit and sends nothing, logs
one line naming the variable and why, and `agent-msg doctor` shows `otlp: disabled (VAR
ignored: reason)`. A bad value of the relay's own settings, by contrast, stops
`relay-watcher` at start-up (exit 1, naming the variable, or the file's key and its line
and column, and never a header value) and is ignored by `agent-msg` and the hooks, so it
can never stop delivery; `agent-msg doctor` warns `watcher_otlp_config_invalid`. Each
value resolves environment, then file, then default. `--once` sends nothing.

**Plain http only.** No TLS library is in the tree, so an `https://` endpoint of the
relay's own settings is refused at start-up with a message naming the key or variable (an
inherited generic one is ignored, see above). The body is OTLP's JSON encoding
(`Content-Type: application/json`, `POST <endpoint>/v1/metrics`), so no protobuf dependency
is needed: the collector must accept OTLP/HTTP JSON on its HTTP receiver (usually port
4318; the gRPC port 4317 will not work). The watcher reads
`OTEL_EXPORTER_OTLP_(METRICS_)PROTOCOL` only to decide whether to honour an inherited
generic endpoint (see above); it never speaks anything but JSON over http.

**Recommended.** Put the collector in the config file and leave the unit unchanged:

```toml
# ~/.ix/relay/config.toml
[watcher]
otlp_endpoint = "http://<collector>/api/v1/otlp"   # a base URL; /v1/metrics is appended
```

A relay endpoint (the file key or `IX_RELAY_WATCHER_OTLP_ENDPOINT`) means the generic
`OTEL_*` variables in the unit's environment are never consulted, so their headers can
never reach it. Without one, a generic `OTEL_EXPORTER_OTLP_PROTOCOL` of `grpc` or
`http/protobuf` in the unit's environment silently disables the generic fallback (with
one log line and an `ignoring` note in `agent-msg doctor`), while a usable inherited
`OTEL_EXPORTER_OTLP_HEADERS` goes with the inherited endpoint it belongs to. Prefer the
config key.

**Notes (non-normative).** Of the emitters found under `~/dev`, `py-observability` exports traces over gRPC to `tempo:4317`, and the local Tempo also has an HTTP receiver on 4318 for traces; no metrics collector was found, so the collector and its acceptance of OTLP/HTTP JSON are to be confirmed with the observability owner. Whether plain http is enough or a TLS dependency should be added is an open question for the owner, recorded in the pull request.

A minimal OpenTelemetry Collector to receive this:

```yaml
receivers:
  otlp:
    protocols:
      http:
        endpoint: 0.0.0.0:4318      # accepts application/json and application/x-protobuf
exporters:
  prometheus:
    endpoint: 0.0.0.0:8889          # or otlphttp / prometheusremotewrite to your store
service:
  pipelines:
    metrics:
      receivers: [otlp]
      exporters: [prometheus]
```

**Resource.** `service.name` (`OTEL_SERVICE_NAME`, else `service.name` in
`OTEL_RESOURCE_ATTRIBUTES`, else `ix-relay-watcher`), `host.name` (the machine's bus
name), `service.version`, and the other `OTEL_RESOURCE_ATTRIBUTES` pairs.

**Series** (also the catalogue in the spec, FR-045; no series carries message text):

| Name | Kind | Unit | Attributes |
|------|------|------|------------|
| `herdr.pane.info` | gauge (1) | `1` | machine, pane, tab, workspace, workspace_label, tab_label, session, bus_name |
| `herdr.pane.status` | gauge (1) | `1` | machine, pane, status |
| `ix.relay.messages` | sum | `{message}` | outcome: delivered, requeued, redelivered, dead_lettered |
| `ix.relay.inbox.depth` | gauge | `{message}` | lead |
| `ix.relay.inbox.oldest_age` | gauge | `s` | lead |
| `ix.relay.inflight.entries` | gauge | `{message}` | lead |
| `ix.relay.deadletter.entries` | gauge | `{message}` | lead |
| `ix.relay.hook.failures.recent` | gauge | `{failure}` | stage, error_kind |
| `ix.relay.watcher.tick.duration` | histogram | `s` | none |
| `ix.relay.registrations` | gauge | `{registration}` | machine |

- Each watcher publishes **its own machine's** panes only, one series per herdr pane with
  an agent (`herdr.pane.status` joins to `herdr.pane.info` on `(machine, pane)`). `bus_name`
  is empty for a pane no lead has registered. A pane herdr lists twice is one series.
- Label values are cleaned of control, bidi and invisible characters, cut to 128
  characters, and JSON-escaped. Panes are read from the layout the watcher already reads
  about every 30 s, so a renamed tab shows within one refresh (and one push); if herdr
  cannot be read the last panes are kept for 90 s and then left out.
- Counters are cumulative since the watcher started. `ix.relay.messages` counts what this
  watcher did or saw: `delivered` (typed into a pane by the watcher, not by a hook),
  `requeued`, `redelivered` and `dead_lettered` (an expired lease that returned to the
  inbox or ran out of redeliveries). Not in phase 1: `sent` and `denied`, a
  `delivery.latency` histogram, escalation counts, in-flight *batches* (entries are
  exported instead: a batch count needs the rows).
- `lead` is bounded: at most 50 leads have series of their own and the rest fold into
  `lead=other`; `agent-msg doctor` reports how many.
- `ix.relay.hook.failures.recent` is a gauge of this machine's failures still in the
  retained `health:hooks` stream that happened since the watcher started; the stream is
  capped, so it falls when old entries are dropped. It is not a counter.

**Cost.** Once per push (30 s by default) the tick adds two pipelined Redis requests, after
its deliveries: one over the local leads' own keys (inbox length and oldest message,
in-flight and dead-letter lengths) and one for the newest hook failures (up to 1,000
entries). There is no key scan, and a failure of either is logged once and leaves those
series out without touching the tick. A tick inside the interval adds nothing.

**How it behaves when the collector does not.** The push runs on its own thread, fed a
queue of two snapshots (the oldest is dropped when full), so a slow or dead collector
never delays a tick, never grows memory and never stops the watcher. Connect timeout 2 s,
whole request 5 s, redirects not followed, a request at most 4 MiB. After a failure it
waits 1 s, doubling to 5 min (or the collector's `Retry-After`, up to 5 min); a 4xx other
than 429 is a refusal of that request and does not back off, and a 2xx that rejects every
point is a failure (`rejected_points`). One log line starts an outage and one ends it. The
heartbeat and `agent-msg doctor` show `otlp: sending to <host:port>` with the exporter's
counters (pushes sent and failed, snapshots dropped, points rejected), `otlp: disabled`
or `otlp: unknown`, and warn `watcher_otlp_failing` (with a reason code such as
`connect_failed`, `timeout`, `http_503`, `rejected_points` or `stuck`) when the collector
cannot be reached; a name lookup has no deadline of its own, so a send that runs over
30 s shows as `stuck`. Header values and endpoint credentials are never printed.

### Installing the watcher

Not installed by this repo. Build and place the binary, then install the unit for
this machine's platform:

```bash
cargo install --path crates/relay-watcher --locked   # installs to ~/.cargo/bin
```

- **node-a, hub** (Linux, systemd): copy `deploy/relay-watcher.service` to
  `~/.config/systemd/user/`, then:
  ```bash
  systemctl --user daemon-reload
  systemctl --user enable --now relay-watcher.service
  ```
- **node-b** (macOS, launchd): copy `deploy/com.agent-ix.relay-watcher.plist` to
  `~/Library/LaunchAgents/`, replacing `YOUR_USER` with the real account name, then:
  ```bash
  launchctl load ~/Library/LaunchAgents/com.agent-ix.relay-watcher.plist
  ```

The watcher does not exit when Redis is unreachable: it retries forever with
exponential backoff (1s, doubling, capped at 30s; reset by the next good poll). It
only exits on a command-line or configuration error at startup. The units still
restart it if it crashes (`Restart=always` / `KeepAlive`); the systemd unit sets
`StartLimitIntervalSec=0` so a crash loop can never leave it permanently `failed`.

Before starting it, put this machine's settings in `~/.ix/relay/config.toml`
(see "Configuration") — in particular `machine`, if the hostname's casing or
domain suffix needs fixing.

### Is the watcher healthy?

`agent-msg doctor` answers this for the whole relay in one read-only command: Redis and its
round-trip time, the watcher heartbeat of this machine and every machine with a lead, the
watcher's state file and unit, hook failures (spooled locally and recorded on the bus),
herdr's version and output shape, registrations, dead letters, in-flight leases and inbox age.
Each line has a stable code, and one that is not `ok` names a likely cause and a fix; `--json`
prints the same as one object for a script. It works with Redis down and finishes within
5 seconds however the bus and the children are failing.

Exit 1 means something needs attention now. Each check is one of `ok`; `fail` (exit 1, for
example a machine that has registered leads and whose watcher ticked in the last 24 hours but
now has no heartbeat, 50 or more hook failures under 15 minutes old or one session failing in
three distinct 15-minute windows of the last hour, or mail waiting under a wedged or missing
watcher); `warn` (reported, exit 0, and exit 1 with `--strict`: dead letters, a pane
herdr no longer has after an hour, a watcher older than the heartbeat, an old herdr with a
readable output, mail waiting while the watcher is fresh); or `unknown` (it could not tell: an
unreadable service manager, herdr not answering; never fails the exit). A machine whose watcher
died stays a failure for the 24-hour prune horizon, using a non-expiring last-tick marker the
watcher wrote, because the leads' own timestamps stop moving when their watcher does. The
catalogue of codes and their severities is in FR-029. The watcher writes its heartbeat to `<prefix>health:watcher:<machine>` after every
good tick, with an expiry of three sweep intervals (at least 30 seconds): a missing key means
no watcher has ticked on that machine recently.

By hand, on Linux (node-a, hub):

```bash
systemctl --user status relay-watcher          # active (running), and since when
journalctl --user -u relay-watcher -e          # what it has logged
journalctl --user -u relay-watcher --since -1h | grep -E 'unreachable|cannot poll|no working poll|is back|polling again'
```

On macOS (node-b), after `launchctl load`:

```bash
launchctl list | grep relay                    # com.agent-ix.relay-watcher, with its pid
tail -n 50 ~/Library/Logs/relay-watcher.log    # StandardOutPath/StandardErrorPath in the plist
grep -E 'unreachable|cannot poll|no working poll|is back|polling again' ~/Library/Logs/relay-watcher.log
```

Silence is normal. Each outage is logged once when it starts (`redis unreachable: ...`,
or `watcher cannot poll: ...` when Redis answers but a poll keeps failing) and once when
it ends (`redis is back after ...` / `watcher polling again after ...`). A per-lead
condition (blocked, stale registration, no agent, herdr error) is logged once when it
starts and once when it ends, not every poll. When an outage reaches 60 seconds the
watcher logs `no working poll for Ns; notifying` and shows one herdr notification.

`~/.ix/relay/state/watcher.json` (next to `config.toml`, or beside `IX_RELAY_CONFIG`)
records `pid`, `started_at_ms`, `last_ok_tick_ms` and `last_error`, so the watcher's
state can be read with Redis down; a `last_ok_tick_ms` more than about 20 seconds old
(the sweep runs every 15) with a running unit means it cannot poll. `relay-watcher --once` never writes it.

## Session work dashboard

Monitor a verified lead session with `team-leader-dashboard --lead luna:SWM:code`.
Add `--session <native-session-id>` to refuse an unexpected occupant at startup.
The monitor keeps the original native session and process binding; restart it to
bind a replacement. It reads independently from Herdr, Linear (using
`LINEAR_API_KEY`) and explicit Redis work reports. It never consumes inboxes or
changes tracker state.

The lead reports assigned scope and actual work:

```bash
agent-msg work --lead luna:SWM:code scope --project ix-board --project ix-projects
agent-msg work --lead luna:SWM:code focus "Reviewing credentials" --ticket SWM-12
agent-msg work --lead luna:SWM:code agent reviewer-1 --ticket SWM-12 --role reviewer --status running
```

Use `agent-msg work --help` for initiative and ticket-subtree selection, worker
pane verification, updates and removal. Scope is explicit, overlapping selectors
count once, and progress counts non-canceled/non-duplicate leaf tasks. Internal
agents have reported status; separate pane activity is observed only when its
native session matches. Ticket workflow stages stay separate from agent status.

Use `t` for Tickets, `a` for Agents, and `p` for Scope. Agents remain visible
without reported scope or Linear data; they show every explicit assignment,
including finished stages and tickets outside scope. Native internal subagents
must be reported by the lead; they are not automatically discovered.
Scope gives each initiative and project a scrollable row with done/total,
remaining, ready and blocked leaf-task counts. Details show remaining workflow
stages and the project's Linear status. All group counts are restricted to the
reported scope; overlapping initiative and project counts must not be added.

Use arrows or j/k to scroll, `d` or Enter for details, `r` for a forced Linear
refresh and `q` to quit. On short panes, details replace the table. The `s` key
shows source timestamps, hidden by default. Last good snapshots survive refresh
errors; error labels remain visible with status hidden. Linear refreshes every
30 minutes, while Herdr and reports refresh every minute.
